# ADR-005: Audit log as a permission-restricted, trigger-protected table

**Status:** Accepted | **Date:** 2026-09-21

**Context:** Audit records must be append-only and unmodifiable by end users, with a read-only "my activity" view — enforced by the system, not just convention. The system has four trust zones: browser code, trusted Next.js server routes acting as a backend-for-frontend (BFF), the core backend service, and the databases. Browser code never receives database credentials or connects directly to a database. The BFF may hold narrowly scoped server-only credentials for infrastructure it owns, such as click-event ingestion, but it does not receive the primary application database credential or write the application audit log. Only the core backend service can access the primary application database.

**Decision:** Store audit records in an `audit_log` table in the primary database. Only the core backend service's audit DB role can write to it — that role has `INSERT`/`SELECT` only, no `UPDATE`/`DELETE`. A DB trigger additionally rejects any update/delete as defense in depth. The user activity view queries this table filtered to the current user and is served by the core backend through the BFF. Next.js server routes must forward authenticated requests and correlation headers but cannot use their separate infrastructure credentials to access this table.

Each audit row's `correlation_id` originates in the **browser**: a UUID generated per user-initiated action (e.g., "submit rating," "run search") and sent as `X-Correlation-ID` on every call that action triggers. The BFF preserves a valid supplied value unchanged when proxying. The core backend validates it and passes it unchanged into `audit_log`. If the header is missing or malformed, the first trusted server component handling the request generates an ID and downstream components preserve it rather than generating another. Missing correlation metadata never blocks the user action or audit write. This ties multiple backend calls from a single browser action together when the browser behaves correctly while retaining traceability for server-originated work.

Product analytics is explicitly outside this audit-correlation contract. Best-effort click events sent to BFF-owned analytics storage use an anonymous browser session identifier and may include an authenticated actor ID when available, but they are not audit records and are not required to carry the action's `X-Correlation-ID`. Analytics delivery may fail or be dropped without affecting the user action. Analytics data must not be used to prove that a security-sensitive or state-changing action occurred; the core backend's append-only `audit_log` is the sole source for that purpose. If analytics later needs cross-system action tracing, that requires a separate ADR covering its privacy, retention, and reliability consequences.

**Alternatives considered:**
- Separate audit microservice / write-once store — stronger long-term, rejected for now as unjustified operational overhead at this scale; natural next step if volume/compliance needs grow.
- App-code-only enforcement — rejected, doesn't stop misuse via direct DB access or future bugs.
- Backend-generated correlation ID per request — simpler, rejected because it can't tie together multiple backend calls belonging to one frontend-side user action.

**Consequences:** Append-only behavior is enforced at two independent layers; only the core backend audit role can write. Server-only credentials in Next.js remain isolated from browser bundles and are scoped to BFF-owned infrastructure, so adding a route does not silently grant access to the primary database. Audit completeness does not depend on optional analytics availability, and analytics cannot be mistaken for compliance or security evidence. Trade-off: audit writes share I/O with the primary workload, backups cover both, and every application proxy hop must preserve correlation metadata. If the browser omits a valid ID, server fallback preserves request-level tracing but cannot reconstruct a multi-request browser action—an accepted gap in exchange for never blocking a real request.
